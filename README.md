# Smart Waste · SPU ขอนแก่น

ระบบแจ้งและติดตามปัญหาขยะล้นในมหาวิทยาลัย (เลือกจุด → ถ่ายรูป → ส่ง) พร้อม **ผู้ช่วยวิเคราะห์ปัญหา (AI-assist)** ที่ประเมินความเร่งด่วน ตรวจชนิดถัง และอธิบายเหตุผล

## ปัญหาและผู้ใช้
- **ปัญหา:** ถังล้นแล้วไม่มีใครรู้ทันที เจ้าหน้าที่ไม่รู้ว่าจุดไหนต้องไปก่อน ขยะค้างนานจนมีกลิ่นและแมลง
- **ผู้ใช้:** ผู้แจ้ง (นักศึกษา/บุคลากร) · เจ้าหน้าที่เก็บขยะ · ผู้ดูแลพื้นที่
- **หลักฐานจากผู้ใช้จริง:** ยังไม่ได้ใส่ ให้เพิ่มผลสำรวจ/ภาพหน้างาน/บทสัมภาษณ์ที่ `PROJECT.evidence` ใน `app.js` (หน้า "โครงงาน" จะแสดงให้เอง) และสรุปไว้ในรายงาน

## ฟีเจอร์
| บทบาท | ทำอะไรได้ |
|---|---|
| ผู้แจ้ง | แจ้งขยะล้น (ต้องแนบรูป) · วิเคราะห์ก่อนส่ง · ติดตามสถานะ · แผนผัง · Dashboard · Chatbot |
| เจ้าหน้าที่ | รับงาน · เปลี่ยนสถานะ · แนบรูปหลังเก็บ · ดูข้อความ LINE (จำลอง) · งานเรียงตามความเร่งด่วน |
| ผู้ดูแลพื้นที่ | ภาพรวมทุกโซน · รับ Escalation · มอบหมายงานใหม่ |

กฎระบบ: รวมเรื่องซ้ำของถังเดียวกันภายใน 30 นาที · เตือนนาทีที่ 20 · ส่งต่อผู้ดูแลนาทีที่ 30 · ปุ่ม "เร่งเวลา +10 นาที" ใช้ทดสอบ

## ผู้ช่วยวิเคราะห์ปัญหา (`ai.js`)
- **ชนิด:** กฎ + พจนานุกรมคำ (rule-based) ไม่ใช่โมเดลที่เรียนรู้เอง ผลเหมือนเดิมทุกครั้งเมื่อข้อมูลเหมือนเดิม
- **ทำอะไร:** ให้คะแนนเร่งด่วน 0–100 → ความรุนแรง ต่ำ/กลาง/สูง · แสดงความมั่นใจ · แนะนำถังที่ตรงชนิดขยะ · แสดงเหตุผลทุกข้อ
- **คะแนน:** พื้นฐานตามประเภทปัญหา (ขยะล้น 48 · มีกลิ่น 42 · ขยะตกพื้น 38 · ถังเต็ม 30) ± คำเสี่ยงสูง/คำบอกว่าไม่รุนแรง · ชนิดถัง · การแจ้งซ้ำใน 24 ชม.
- **ข้อมูลไม่พอ:** ถามเพิ่มและแสดงความมั่นใจต่ำ · **นอกขอบเขต:** แจ้งว่าวิเคราะห์ไม่ได้ ไม่เดาคำตอบ
- **Dashboard:** วิเคราะห์จุดเสี่ยง (ต้องมีอย่างน้อย 3 เรื่อง ไม่งั้นแจ้งว่าข้อมูลน้อย)
- **ข้อจำกัด:** ไม่ดูรูปภาพ · เข้าใจเฉพาะคำในพจนานุกรม · เกณฑ์ยังไม่ปรับเทียบกับข้อมูลหน้างานจริง

### ทางเลือกอื่นที่พิจารณา
| ทางเลือก | ข้อดี | ข้อจำกัด |
|---|---|---|
| กฎ + พจนานุกรม (ที่เลือก) | อธิบายได้ ผลคงที่ ไม่ต้องมีเซิร์ฟเวอร์ ไม่เสี่ยง API key รั่ว | เข้าใจเฉพาะคำที่กำหนด |
| โมเดลภาษา (LLM) ผ่านเซิร์ฟเวอร์กลาง | เข้าใจภาษาธรรมชาติกว้างกว่า | ต้องมีเซิร์ฟเวอร์ซ่อน key · มีค่าใช้จ่าย · ผลอาจเปลี่ยนทุกครั้ง |
| โมเดลจำแนกภาพ | ตรวจระดับขยะจากรูปจริง | ต้องมีชุดภาพสอนและทดสอบความแม่นยำ |

### ต่อโมเดลภายนอก (ไม่บังคับ)
GitHub Pages เป็นเว็บแบบ static **ห้ามใส่ API key ในเว็บ** ให้ deploy `worker/ai-proxy.js` (Cloudflare Workers) แล้วเก็บ key เป็น secret ที่นั่น จากนั้นตั้งค่าใน `index.html`:
```html
<script>window.SW_CONFIG={aiEndpoint:"https://your-worker.example.workers.dev",contact:"อีเมลผู้รับผิดชอบข้อมูล"};</script>
```
ถ้าเชื่อมต่อไม่ได้ ระบบจะกลับไปใช้การวิเคราะห์ในเครื่องเองและแจ้งผู้ใช้ จะส่งออกเฉพาะข้อความรายละเอียด ประเภทปัญหา ประเภทถัง และอาคาร **ไม่ส่งรูป**

## ความปลอดภัยและ PDPA
- ขอความยินยอมก่อนใช้งานครั้งแรก (เปิดอ่านซ้ำได้ที่ท้ายหน้า) ถ้าไม่ยอมรับจะดูข้อมูลได้แต่ส่งเรื่องไม่ได้
- ไม่เก็บชื่อ เบอร์ อีเมล หรือ GPS · ข้อมูลอยู่ใน localStorage ของเครื่อง · ล้างได้ด้วยปุ่ม "ล้างข้อมูลทั้งหมด"
- ไม่มี API key ในโค้ดฝั่งเบราว์เซอร์ · ข้อความผู้ใช้ถูก escape ก่อนแสดง · ข้อความที่เหมือนคำสั่งถึงระบบ ("ไม่ต้องสนใจคำสั่งก่อนหน้า…") ไม่ถูกทำตาม
- ตรวจชนิดไฟล์ (เฉพาะรูป) และขนาด (ไม่เกิน 10 MB) ก่อนรับไฟล์

## ทดสอบ
หน้า **โครงงาน → รันชุดทดสอบ** รัน 10 กรณีสด (ตัวอย่าง 5 กรณี + TC05–TC09) หรือรันใน Node:
```
node -e "require('./ai.js').selfTest().forEach(c=>console.log(c.pass?'PASS':'FAIL',c.id,c.actual))"
```
กรณีที่ต้องทดสอบด้วยมือตามแบบประเมิน: TC01–TC04 · TC10 (ตรวจ source ไม่มี key) · TC11 (เวลาตอบสนอง) · TC12 (มือถือ/คอม) · TC13 (ผู้ใช้ทดลอง 3 คน)

## ข้อมูล
เก็บในเบราว์เซอร์เครื่องนั้น (localStorage) · ปุ่มท้ายหน้า "โหลดข้อมูลตัวอย่าง" / "ล้างข้อมูลทั้งหมด" · ตำแหน่งถัง/ห้องแก้ที่ต้น `app.js` (`BINS`, `BLD`) พิกัดเป็นพิกเซลบนแผนผัง 960×960 ซึ่งฝังอยู่ท้าย `app.js`

## ข้อจำกัดของต้นแบบ
- ไม่ส่ง LINE จริง แสดงเป็นหน้าตาข้อความเท่านั้น
- ตำแหน่งถังเป็นตำแหน่งตัวอย่างบนแผนผัง
- ข้อมูลอยู่ในเครื่องเดียว ไม่ซิงก์ข้ามอุปกรณ์ จึงยังไม่มีระบบล็อกอิน
